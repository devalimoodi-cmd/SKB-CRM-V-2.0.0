# اسنپ‌شات ساختار دیتابیس (Schema Snapshot)

فایل‌های `schema-YYYY-MM-DD.sql` ساختار کامل دیتابیس (بدون داده) هستند که با
`npm run db:schema` از دیتابیس فعلی گرفته می‌شوند.

## گرفتن اسنپ‌شات جدید

```bash
npm run db:schema
```
- از `pg_dump` استفاده می‌کند (پیش‌فرض روی ویندوز: `C:\Program Files\PostgreSQL\18\bin\pg_dump.exe`).
- اگر pg_dump جای دیگری است: در `.env` مقدار `PG_DUMP_PATH` را ست کن.

## بازیابی روی سرور جدید

با `psql` (یا Query Tool در pgAdmin) فایل SQL را روی دیتابیس خالی اجرا کن:

```bash
psql -U postgres -h localhost -d "SKB-CRM" -f db/schema-2026-09-14.sql
```

سپس در پوشهٔ Backend:
```bash
npm run db:migrate     # اعمال مایگریشن‌های جدید (اگر بعد از اسنپ‌شات اضافه شده‌اند)
```

> نکته: داده‌ها (مشتری‌ها، سالن‌ها، کاربران…) در این فایل نیستند و
> باید جداگانه بکاپ/ریستور شوند (`pg_dump -Fc` برای بکاپ کامل).

# بکاپ روزانه (دیتابیس + فایل‌ها)

دستور `npm run backup` (یا `backup.bat` در ریشهٔ پروژه) یک بکاپ کامل می‌سازد:

```
backups\2026-09-14_10-30\
  ├─ db.dump      ← بکاپ دیتابیس با pg_dump -Fc (قابل ریستور با pg_restore)
  ├─ uploads\     ← همهٔ فایل‌های آپلودشده
  └─ info.json    ← تاریخ و مشخصات بکاپ
```

- هر بار یک پوشهٔ تاریخ‌دار ساخته می‌شود و فقط **۷ نسخهٔ آخر** نگه داشته می‌شود (`BACKUP_KEEP` در `.env`).
- فقط پوشه‌هایی که خودِ اسکریپت ساخته (الگوی `YYYY-MM-DD_HH-MM`) پاک می‌شوند؛ هر پوشه/فایل دیگری که خودت داخل `backups` بگذاری دست‌نخورده می‌ماند.
- لاگ در `logs/backup.log` نوشته می‌شود.

## کپی خودکار روی دیسک دوم (مهم)

بکاپی که فقط روی همان دیسک دیتابیس باشد، در خرابی دیسک بی‌فایده است. در `.env` این را ست کن:

```ini
BACKUP_COPY_TO=E:\SKB-Backups      # دیسک دوم یا \\server\share\SKB-Backups
BACKUP_KEEP=7
```

با هر بکاپ:
1. پوشهٔ بکاپ به مسیر دوم کپی می‌شود.
2. **صحت کپی بررسی می‌شود** (هم‌اندازه بودن `db.dump` و تعداد فایل‌ها).
3. نسخه‌های قدیمی هر دو مسیر پاک می‌شوند (فقط پوشه‌های بکاپ).
4. اگر کپی ناقص/ناموفق باشد، اسکریپت با کد خطا (exit 1) تمام می‌شود تا در لاگ/Task ببینی.

## زمان‌بندی خودکار (Task Scheduler)

فایل `install-backup-task.bat` در ریشهٔ پروژه (با **Run as administrator**):

```bat
install-backup-task.bat install              :: بکاپ روزانه ساعت 02:00
install-backup-task.bat install 23:30        :: ساعت دلخواه
install-backup-task.bat install 02:00 system :: اجرا با حساب SYSTEM (بدون نیاز به لاگین کاربر)
install-backup-task.bat status               :: مشاهدهٔ وضعیت تسک‌ها
install-backup-task.bat uninstall            :: حذف تسک‌ها
```

دو تسک ساخته می‌شود: «بکاپ روزانه» و «گزارش هفتگی حجم uploads».
حتماً بعد از نصب یک‌بار دستی `backup.bat` را اجرا کن و `logs/backup.log` را ببین (و یک‌بار ریستور را روی دیتابیس تستی تمرین کن).

## ریستور بکاپ

```bash
# دیتابیس (روی دیتابیس خالی)
pg_restore -U postgres -h localhost -d "SKB-CRM" --clean --if-exists backups/2026-09-14_10-30/db.dump

# فایل‌ها
# محتوای backups/2026-09-14_10-30/uploads را داخل Backend/uploads کپی کن
```

> انتقال بکاپ به یک دیسک/سرور دیگر را فراموش نکن (بکاپ روی همان دیسک، محافظ خوبی نیست).

# نگهداری فایل‌های آپلودی (uploads)

پوشهٔ `Backend/uploads` با گذشت زمان بزرگ می‌شود (پیوست گزارش بازدید می‌تواند ویدیو تا ۵۰۰MB باشد).
دو اسکریپت امن برای مدیریت آن وجود دارد:

## ۱) گزارش (فقط خواندنی)

```bat
uploads-report.bat                    :: یا: npm run uploads:report
uploads-report.bat --older-than=180   :: فایل‌های قدیمی‌تر از ۱۸۰ روز
uploads-report.bat --json             :: خروجی JSON (برای اتوماسیون)
```

نمایش می‌دهد: تعداد/حجم کل، تفکیک هر پوشه، ۱۰ فایل بزرگ، فضای آزاد دیسک،
فایل‌های قدیمی، **تعداد فایل‌های یتیم** (فایلی که در دیتابیس ارجاعی ندارد) و
**ارجاع‌های بدون فایل** (رکورد دیتابیس که فایلش روی دیسک نیست → تصویر/پیوست خراب).
خروجی در `logs/uploads-report.log` ذخیره می‌شود.

## ۲) پاک‌سازی فایل‌های یتیم

«یتیم» = فایلی که در `uploads` هست ولی مسیر/نامش در هیچ ستون متنی/JSON دیتابیس
پیدا نمی‌شود (مثلاً پیوستی که رکوردش حذف شده).

```bat
clean-orphans.bat                                  :: فقط نمایش — هیچ فایلی حذف نمی‌شود (امن)
clean-orphans.bat --delete                         :: حذف واقعی
clean-orphans.bat --delete --min-age-hours=48      :: فقط فایل‌های قدیمی‌تر از ۴۸ ساعت
```

🛡️ محافظ‌ها:
- پیش‌فرض **dry-run** است؛ بدون `--delete` چیزی پاک نمی‌شود.
- فایل‌های تازه‌تر از `ORPHAN_MIN_AGE_HOURS` (پیش‌فرض ۲۴ ساعت) هرگز حذف نمی‌شوند
  (تا فایلی که همین حالا آپلود شده ولی رکوردش در حال ثبت است، پاک نشود).
- **دارایی‌های ثابت برنامه** (مثل `avatar-01.jpg`) هرگز یتیم حساب نمی‌شوند. الگوهای
  پیش‌فرض: `avatar-N.jpg`، `default-avatar.*`، `.gitkeep`، `.gitignore`، `README*`.
  الگوی دلخواه را با کاما در `UPLOADS_KEEP_PATTERNS` (regex) اضافه کن.
- فقط داخل پوشهٔ `uploads` حذف می‌شود (بررسی مسیر).
- فهرست کامل هر اجرا در `logs/orphan-uploads-<تاریخ>.txt` ذخیره می‌شود — اول همان را ببین.

> روتین پیشنهادی: هفتگی `uploads-report.bat` را ببین؛ ماهی یک‌بار اگر عدد یتیم‌ها
> قابل توجه بود، `clean-orphans.bat` را اجرا کن، فایل گزارش را بازبینی کن و بعد `--delete`.

# جدول‌های «نظرات و پیشنهادات» (suggestions / suggestion_messages)

اولین مایگریشن پروژه: `Backend/migrations/20260915120000-create-suggestions.js`

```bash
npm run db:migrate   # ساخت جدول‌ها (idempotent: اگر باشند، دوباره ساخته نمی‌شوند)
npm run db:schema    # به‌روزرسانی اسنپ‌شات ساختار (db/schema-*.sql)
```

| جدول | کاربرد |
|---|---|
| `suggestions` | سرِ گفتگو: کاربر، نوع پیام، وضعیت، `admin_unread`، `user_unread`، شمارنده و آخرین پیام |
| `suggestion_messages` | پیام‌های گفتگو: `sender_type` (user/admin)، متن، `read_at` (رسید خواندن) |

- حذف یک گفتگو با `DELETE /api/suggestions/:id` انجام می‌شود و پیام‌هایش هم پاک می‌شوند.
- حذف یک پیام با `DELETE /api/suggestions/:id/messages/:messageId` (فقط ادمین): بعد از حذف،
  `messages_count` و `last_message_at`/`last_sender` بازمحاسبه می‌شوند؛ پیام اول گفتگو به‌صورت
  تکی قابل حذف نیست (برای آن کل گفتگو را حذف کن) و اگر آخرین پیام حذف شود کل گفتگو پاک می‌شود.
- **ضد تکرار (ضد ارسال دوبار):** `POST /api/suggestions` اگر همان کاربر در ۳۰ ثانیهٔ اخیر همان
  «عنوان + متن» را فرستاده باشد، رکورد جدید نمی‌سازد و همان گفتگو را با `duplicate: true`
  برمی‌گرداند (محافظ در برابر دابل‌کلیک/دابل‌تپ/retry شبکه).
- ⚠️ قبل از اجرای مایگریشن روی سرور، یک بکاپ بگیر (`backup.bat`).

# همگام‌سازی مدل‌ها با دیتابیس (sync): **هرگز**

> ⚠️ در این پروژه `sequelize.sync` **عمداً غیرفعال** است
> (در `config/database.js` کامنت شده و در `migrations/README.md` هم تأکید شده).
> **هر تغییر ساختار دیتابیس باید به‌صورت مایگریشن انجام شود.**

## چرا sync نمی‌زنیم؟
1. `sync({ alter: true })` (که در `scripts/sync-db.js` استفاده شده) ساختار ستون‌ها/ایندکس‌ها را
   «مطابق مدل‌های فعلی» تغییر می‌دهد و می‌تواند روی دیتابیس واقعی، **ستون یا ایندکس را حذف/نوع را عوض کند**.
2. مایگریشن هدفمند، قابل بازبینی، قابل برگشت (`db:rollback`) و **ثبت‌شده در جدول `SequelizeMeta`** است.
3. ساختار فعلی دیتابیس از `db/schema-*.sql` هم قابل بازسازی است.

## مسیر درست تغییر ساختار
```bash
npx sequelize-cli migration:generate --name add-some-column-to-halls
# سپس up/down را کامل کن
npm run db:migrate
```

## چک‌لیست استقرار (روی سرور)
```bat
backup.bat                :: ۱) بکاپ (دیتابیس + فایل‌ها)
deploy.bat                :: ۲) کد + پکیج‌ها + مایگریشن + تأیید  (یا: deploy.bat --no-git --no-npm)
npm run db:migrate        ::    (اگر فقط مایگریشن لازم است)
npm run db:verify         :: ۳) تأیید خواندنی: جدول‌ها، ستون‌ها، ایندکس‌ها، مایگریشن‌ها
:: ۴) ری‌استارت هر دو سرویس
```
- `deploy.bat` همهٔ این‌ها را به ترتیب انجام می‌دهد و در صورت خطا با کد غیرصفر خارج می‌شود.
- اگر در `.env` مقدار `BACKUP_BEFORE_MIGRATE=1` باشد، `deploy.bat` قبل از مایگریشن خودش بکاپ می‌گیرد.

# 🔴 عیب‌یابی: خطای ۵۰۰ پس از استقرار (جدول/ستون وجود ندارد)

**نشانه:** پس از مستقر کردن روی سرور، بعضی بخش‌ها (معمولاً «نظرات و پیشنهادات» یا صفحه‌های تازه)
خطای `۵۰۰ Internal Server Error` می‌دهند و پیام فارسی آن‌ها همین است:
«خطای داخلی سرور رخ داد. لطفاً چند لحظه بعد دوباره تلاش کنید.»

**چرا پیام مفید نیست؟** در `NODE_ENV=production` هر خطای ۵xx در `utils/response.js`
**ماسک** می‌شود تا جزئیات دیتابیس لو نرود؛ خطای واقعی فقط در `logs/backend.log` سرور است.

**علت شایع:** مایگریشن‌ها روی دیتابیس سرور اجرا نشده‌اند (یا روی دیتابیس دیگری اجرا شده‌اند):
```
SequelizeDatabaseError: relation "suggestions" does not exist
```

**بررسی و رفع (روی سرور):**
```bat
cd Backend
npm run db:status      :: کدام مایگریشن‌ها اجرا نشده‌اند؟ (ستون down)
npm run db:migrate     :: اجرای مایگریشن‌ها
npm run db:verify      :: ✅ باید ALL PASS بدهد
```
سپس بک‌اند را ری‌استارت کن.

**تأیید از مرورگر (بدون دسترسی به سرور):** با توکن ادمین این آدرس را باز کن:
```
GET /api/server-status
```
در بلوک `data.schema` دقیقاً می‌بینی:
```json
{ "ok": false, "missingTables": ["suggestions", "suggestion_messages"],
  "appliedMigrations": 0, "totalMigrations": 1, "pendingMigrations": ["20260915120000-create-suggestions.js"],
  "hint": "روی سرور اجرا کن:  npm run db:migrate  سپس  npm run db:verify" }
```

⚠️ **نکتهٔ مهم:** `.env` سرور باید همان دیتابیسی را نشان دهد که خود بک‌اند استفاده می‌کند
(`DB_HOST`/`DB_NAME`). اگر مایگریشن با `.env` دیگری اجرا شود، سایت همان خطا را می‌دهد.
یادآوری: `sequelize.sync` هرگز مجاز نیست — رجوع به بالای همین فایل.

**اسکریپت‌های استقرار قدیمی:** اگر روی سرور اسکریپتی دارید که `node sync-db.js`
(در ریشهٔ `Backend`) را صدا می‌زند، **دیگر کار نمی‌کند** (فایل به `Backend/scripts/sync-db.js`
منتقل شده است) و مهم‌تر اینکه هیچ‌وقت مایگریشن را اجرا نمی‌کرد — همین باعث خطای ۵۰۰ بالا می‌شود.
از `deploy.sh` (لینوکس/PM2) یا `deploy.bat` (ویندوز) استفاده کنید؛ آن‌ها `db:migrate` + `db:verify`
را با توقف روی خطا اجرا می‌کنند.

## پس `db:sync` به چه کار می‌آید؟
فقط برای **دیتابیس‌های خیلی قدیمی (legacy)** و به‌صورت یک‌باره، آن هم **بعد از بکاپ**:
- اصلاح رکوردهایی که `created_by/updated_by` آن‌ها به کاربر ناموجود اشاره می‌کند
- حذف ایندکس‌های یکتای قدیمی (`unique_flock_number_per_customer` و ایندکس‌های `flock_completions`)
- ساخت سکوئنس `customer_code_seq` و اختصاص `customer_code` به مشتریان بدون کد
برای دیتابیس‌های فعلی (که این موارد را دارند) **لازم نیست**.

# تنظیمات سیستم (`app_settings`)

تنظیماتی که ادمین از پنل → «تنظیمات سیستم» تغییر می‌دهد در جدول key/value یعنی
`app_settings` ذخیره می‌شوند. **هیچ مایگریشنی برای اضافه کردن یک تنظیم جدید لازم نیست**؛
فقط کلید را در `Backend/controllers/settingsController.js` داخل `KEY_DEFS` تعریف کن.

| کلید | نوع | پیش‌فرض | کاربرد |
|---|---|---|---|
| `auto_welcome_sms` | boolean | `true` | ارسال خودکار پیامک خوش‌آمدگویی بعد از ثبت مشتری |
| `loader_style` | enum (`classic` / `logo`) | `classic` | لودر سیستمی: دایرهٔ چرخان یا لوگوی ستاره کیان |

اندپوینت‌ها:
- `GET /api/settings` → همهٔ تنظیمات (نیاز به ورود)
- `PUT /api/settings/:key` → تغییر یک تنظیم (مدیر میانی/مدیر اصلی/سوپر ادمین)
- `GET /api/public/ui-settings` → **عمومی (بدون ورود)** فقط کلیدهای نمایشی مثل `loader_style`

> ⚠️ هر کلید جدید که به لیست عمومی (`PUBLIC_KEYS`) اضافه می‌شود باید بی‌خطر و نمایشی باشد.
> مقادیر نامعتبر (مثل `loader_style="x"`) خودکار به مقدار پیش‌فرض برمی‌گردند.

# تست‌های دیتابیسی

تست‌های `npm run test:db`، `npm run test:uploads`، `npm run test:integrity` و
`npm run test:uploads-maint` به **دیتابیس واقعی** وصل می‌شوند (تست یکپارچگی تراکنش‌ها و
تست نگهداری/بکاپ در پوشهٔ موقت %TEMP% کار می‌کنند و به فایل‌های واقعی دست نمی‌زنند).
به همین دلیل به‌صورت پیش‌فرض **SKIPPED** می‌شوند و فقط با اجازهٔ صریح اجرا می‌شوند:

```bat
set ALLOW_DB_TESTS=true
npm run test:db
npm run test:uploads
npm run test:integrity
npm run test:uploads-maint
```

⚠️ روی سرور اصلی (production) اجرا نشوند. تست‌های بدون دیتابیس همیشه قابل اجرا هستند:
`npm run test:security` و `npm run lint`.
