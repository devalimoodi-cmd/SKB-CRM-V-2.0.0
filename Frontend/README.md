# SKB-CRM — Frontend (سایت + پروکسی API)

این سرویس دو کار می‌کند:
1. فایل‌های استاتیک سایت (`HTML/CSS/JS`) را سرو می‌کند.
2. `/api/*` و `/uploads/*` را به بک‌اند (Express روی پورت ۵۰۰۰) **پروکسی** می‌کند تا
   مرورگر همه‌چیز را از یک مبدأ (same-origin) بگیرد.

---

## اجرا

```bat
:: ریشهٔ پروژه (توصیه‌شده — خودش API_URL و PROXY_STRICT را ست می‌کند و در حلقه ری‌استارت می‌شود)
start-frontend.bat

:: یا مستقیم
cd Frontend
npm start
```

متغیرهای محیطی مهم:

| متغیر | پیش‌فرض | توضیح |
|---|---|---|
| `PORT` | `3000` | پورت سایت |
| `API_URL` | `http://127.0.0.1:5000/api` | آدرس بک‌اند |
| `PROXY_STRICT` | `false` | اگر `true` باشد **فقط** `API_URL` استفاده می‌شود (بدون fallback پنهان به پورت ۵۰۰۰/آی‌پی دیگر) |
| `PROXY_TIMEOUT_MS` | `600000` | مهلت پروکسی (برای آپلود ویدیو تا ۵۰۰MB) |

> ⚠️ نکتهٔ مهم: اگر `PROXY_STRICT=false` باشد و بک‌اند اصلی خواب باشد، درخواست‌ها
> بی‌صدا به کاندیدهای بعدی می‌روند و ممکن است تا دقایق معلق بمانند. روی سرور واقعی
> همیشه `PROXY_STRICT=true` بگذار (در `start-frontend.bat` ست شده است).

## کش و نسخه‌دهی دارایی‌ها

هنگام سرو هر صفحه، به آدرس **CSSها و اسکریپت‌های کلاسیک** محلی یک `?v=<ASSET_VERSION>`
اضافه می‌شود (نسخه از جدیدترین زمان تغییر فایل‌ها ساخته می‌شود) — بدون تغییر دستی فایل‌های HTML.

| نوع فایل | هدر کش |
|---|---|
| `CSS` و اسکریپت کلاسیک با `?v=` | `public, max-age=31536000, immutable` (یک‌ساله، بدون درخواست دوباره) |
| ماژول‌ها (`script type="module"`) و importهای داخلی | `private, max-age=60, must-revalidate` (+ ETag → پاسخ ۳۰۴ سبک) |
| تصاویر/فونت‌ها | `public, max-age=86400` |
| صفحات HTML | `no-cache` (همیشه تازه، با ETag) |

### ⛔ قاعدهٔ مهم: URL ماژول‌های ES را هرگز نسخه‌دار نکن

مرورگر ماژول‌های ES را **با URL** شناسایی می‌کند. اگر تگ HTML آدرس
`/features/messages/messages.service.js?v=123` بدهد ولی همان فایل جایی با
`import "../../../features/messages/messages.service.js"` (بدون `?v=`) صدا زده شود،
مرورگر دو ماژول جدا می‌سازد و فایل **دو بار اجرا** می‌شود. نتیجهٔ آن: دو نمونهٔ سینگلتون،
**دو شنوندهٔ click روی یک دکمه** و دو درخواست برای یک کلیک.

> این باگ در عمل رخ داده بود: در صفحهٔ «تماس با ما» یک کلیک روی «ارسال پیام» دو پیام ثبت
> می‌کرد (اختلاف زمانی رکوردها ۴ تا ۱۴ میلی‌ثانیه بود).
>
> به همین دلیل در `server.js` تابع `rewriteAssetUrls` فقط `href`های CSS و تگ‌های
> `<script src>` **بدون** `type="module"` را نسخه‌دار می‌کند. تست `npm run test:cache`
> این قاعده را بررسی می‌کند (`modules=17 versioned=0`).

**نتیجهٔ عملی:** بعد از هر تغییر کد، فقط سرور را ری‌استارت کن؛ نسخهٔ آدرس‌ها عوض
می‌شود و مرورگر کاربران خودش فایل‌های جدید را می‌گیرد (نیازی به «کش را پاک کن» نیست).

## دستورها

```bat
npm start          :: اجرای سرور
npm run lint       :: بررسی کد مرورگر (ESLint) — باید ۰ error و ۰ warning بدهد
npm run test:cache :: تست نسخه‌دهی/کش/۳۰۴ + نگهبان پیام‌های کاربر (بدون بک‌اند/دیتابیس)
npm run test:toast :: تست «توست کم‌مزاحمت» notifyOnce (ضدتکرار/سقف نرخ/خاموشی)
npm run test:denied       :: تست پیام ۴۰۳ و هم‌راستاشدن UI با مجوزها
npm run test:weekly       :: تست موتور محاسبات هفتگی + تجمیع «کل گله» + گروه‌های شاخص + مبنای پایان دوره + حسابرسی/انتخاب هفته‌ها
npm run test:weekly:report :: اسموک‌تست رندر گزارش (گروه‌ها + هشدارها + انتخاب هفتهٔ هر گله)
npm run test:weekly:groups :: تست منطق مودال‌های انتخاب (شاخص‌ها و هفته‌ها: پیش‌فرض/ذخیره/مقدار خراب)
npm run test:weekly:history :: تست رندر گزارش تاریخچه هفتگی (انتخاب گروه‌ها و هفته‌های هر گله)
npm run test:customer-fields   :: تست فیلدهای فرم مشتری (کد ملی/فیلتر ورودی)
npm run test:customer-detail   :: تست مودال «جزئیات مشتری» (خلاصهٔ عملکرد، دوره‌ها، سالن‌ها، FCR)
```

`npm run lint` خطاهای واقعی مرورگر را می‌گیرد (مثلاً استفاده از `Buffer` که در مرورگر
وجود ندارد، یا متغیر تعریف‌نشده). اگر خواستی هشداری را آگاهانه نگه داری، از
`// eslint-disable-next-line <rule>` با توضیح استفاده کن.

## لودر سیستمی (دو حالت قابل انتخاب از پنل ادمین)

هنگام باز شدن صفحه‌های سنگین، یک لودر تمام‌صفحه نمایش داده می‌شود که **دو حالت** دارد و
از پنل ادمین → **تنظیمات سیستم** انتخاب می‌شود:

| حالت | توضیح |
|---|---|
| `classic` | دایرهٔ چرخان (لودر قبلی سیستم) |
| `logo` | لوگوی ستاره کیان + سه حلقهٔ چرخان + هالهٔ نوری + سه نقطه |

متن هر دو حالت یکسان است: **«در حال بارگذاری...»**

### صفحه‌هایی که لودر دارند (لیست سفید)
`dashboard.html` (مسیر `/`)، `customer-list.html`، `customer-info.html`، `admin-panel.html`
— یعنی همان صفحه‌هایی که راه‌اندازی برنامه در آن‌ها زمان‌بر است.

### فایل‌های مربوطه
| فایل | کار |
|---|---|
| `src/shared/components/Loader/loader.html` | مارک‌آپ هر دو حالت (منبع واحد — پنل ادمین از همین فایل پیش‌نمایش می‌سازد) |
| `src/shared/components/Loader/loader.css` | CSS هر دو حالت + کلاس `skb-loader--force-show` برای پیش‌نمایش |
| `server.js` → `injectPageLoader()` | تزریق `data-loader` روی `<html>` + CSS + بلوک لودر در HTML |
| `src/features/admin-panel/*` | کارت «لودر سیستمی» در تنظیمات سیستم (پیش‌نمایش زنده + ذخیرهٔ فوری) |

### چطور کار می‌کند؟
1. ادمین در پنل، یکی از دو کارت پیش‌نمایش را کلیک می‌کند →
   `PUT /api/settings/loader_style` (کلید `loader_style` در جدول `app_settings`).
2. سرور فرانت‌اند هر ۶۰ ثانیه (و در شروع) مقدار را از اندپوینت **عمومی**
   `GET /api/public/ui-settings` می‌خواند و کَش می‌کند (اگر بک‌اند خواب بود → مقدار قبلی،
   و در نهایت `classic`).
3. هنگام سرو هر صفحه از لیست سفید، `data-loader="classic|logo"` روی تگ `<html>` و بلوک
   لودر بلافاصله بعد از `<body>` تزریق می‌شود → نمایش **بدون فلاش** و مستقل از JS.
4. مخفی کردن لودر: صفحه‌های موجود خودشان `#pageLoadingOverlay` را محو می‌کنند و یک
   **مخفی‌کنندهٔ امن** (`window.hidePageLoader()` با سقف ۱۵ ثانیه) هم تزریق می‌شود تا لودر
   هرگز گیر نکند (پنل ادمین پس از آماده شدن، خودش `hidePageLoader()` را صدا می‌زند).

> پیش‌نمایش سریع بدون تغییر تنظیم: `http://127.0.0.1:3000/dashboard.html?loader=logo`

### ✅ **همهٔ** لودرهای سیستم یک منبع دارند (`loader.service.js`)
هر لودری در برنامه — تمام‌صفحه، داخل جدول/کارت/پنل، و مودال سوئال — **پیرو همان انتخاب ادمین** است.
سه اندازه وجود دارد:

| اندازه | کاربرد | روش استفاده |
|---|---|---|
| `full` | اورلی تمام‌صفحه (صفحه‌های سنگین) | خودکار توسط سرور تزریق می‌شود |
| `md` | کارت‌های بزرگ و **مودال سوئال** | `notificationService.showLoading("نـ...")` یا `loaderService.inline({ size: "md" })` |
| `sm` | جدول/کارت/پنل/لیست‌ها | placeholder یا `loaderService.inline({ size: "sm" })` |

دو روش استفاده در کد:

```html
<!-- ۱) استاتیک در HTML: خودکار پر می‌شود (متن و اندازه اختیاری) -->
<span data-skb-loader data-skb-loader-size="sm" data-skb-loader-text="در حال بارگذاری..."></span>
```

```js
// ۲) داینامیک در JS
container.innerHTML = await loaderService.inline({ text: "در حال بارگذاری...", size: "sm" });
// یا بعد از رندر یک لیست داینامیک:
await loaderService.hydrate(container);
```

> ⚠️ اسپینرهای اختصاصی (مثل `.table-loading .spinner` / `.chart-loading .spinner` /
> `fa-spinner` در لودرهای بخشی) حذف شدند تا در کل سیستم یک لودر داشته باشیم.
> فقط اسپینر داخل **دکمه‌ها** (حالت «در حال ذخیره...») طبق قرارداد قبلی باقی مانده است.
> برای افزودن لودر تازه: همان placeholder را در HTML (یا `inline()` در JS) استفاده کن —
> نیازی به کد اضافه یا ایمپورت دستی نیست (سرویس خودکار راه‌اندازی می‌شود).

### پیش‌نمایش در پنل ادمین
- دو کارت پیش‌نمایش (کلاسیک / لوگو) با اندازهٔ درست و بدون بریدگی.
- دکمهٔ **«نمایش تمام‌صفحه»** روی هر کارت: اورلی واقعی را ۳ ثانیه نشان می‌دهد (بدون ذخیرهٔ تنظیم).
- کارت‌ها با `div role="button" tabindex="0"` هستند (نه `button`) تا لودر داخلشان سالم رندر شود؛
  پشتیبانی کیبورد (Enter/Space) هم دارد.

## پیام‌ها و دیالوگ‌ها (SweetAlert2)

- **همهٔ** پیام‌های موفقیت/خطا/هشدار و **تأیید عملیات** از `core/services/notification.service.js`
  استفاده می‌کنند (`notificationService.success/error/warning/info/confirm/showError`) که روی
  **SweetAlert2** ساخته شده است؛ ظاهر همهٔ پیام‌ها یکدست و فارسی است.
- ⛔ **دیالوگ بومی مرورگر ممنوع است** (`alert` / `confirm` / `prompt`). برای اینکه دیگر کسی
  به‌طور تصادفی از آن‌ها استفاده نکند، قاعدهٔ ESLint **`no-alert`** روی کل پروژه فعال شده و
  `npm run lint` هر استفادهٔ جدید را به‌صورت error می‌گیرد.
- تنها استثنا: فالبک‌های مستند داخل `notification.service.js` (وقتی SweetAlert2 در صفحه لود نشده
  باشد) که با `// eslint-disable-next-line no-alert` علامت خورده‌اند.
- نمونهٔ تأیید عملیات (هم‌سبک با حذف‌های پنل ادمین):
  ```js
  const confirmed = await notificationService.confirm({
    title: "🗑️ حذف گفتگو",
    text: "این گفتگو و همهٔ پیام‌های آن حذف شود؟",
    confirmText: "بله، حذف شود",
    cancelText: "انصراف",
  });
  if (!confirmed) return;
  ```
  گزینه‌های اختیاری: `html` (برای متن چندخطی) و `danger: true` (دکمهٔ تأیید قرمز).


### سیاست «هیچ مزاحمتی برای کاربر» — کجا توست، کجا مودال، کجا هیچ

| موقعیت | ابزار | دلیل |
|---|---|---|
| کاربر کلیک کرده و عملیات **شکست خورده** (ذخیره/تغییر وضعیت/رفرش بخش) | `notifyOnce({...})` → **توست** | پیام کوتاه خودبسته، بدون دکمه |
| دادهٔ لازم یک بخش نیست (شناسهٔ مشتری، جدول، کپچا، بوت کند) | **توست** (warning/error) | کاربر باید بداند چرا خالی است |
| خطاهای اعتبارسنجی فرم (لیست چندخطی) | `showError()` → مودال | خواندنی است و کاربر باید اصلاح کند |
| تأیید عملیات مخرب (حذف/غیرفعال‌سازی) | `confirm()` → مودال | تصمیم کاربر لازم است |
| **انقضای نشست (۴۰۱)** | مودال یک‌بارمصرف در صفحهٔ ورود | کاربر باید بفهمد چرا به صفحهٔ ورود آمده |
| **مجوز بسته — عملیات (۴۰۳)** | `notifyOnce()` → **توست** | «دسترسی «حذف سالن» برای نقش شما بسته است» — کوتاه و ضدنکرار |
| **مجوز بسته — ورود به صفحه** | `modalMessage()` → **مودال تک‌دکمه‌ای** (یک‌بار در نشست) | کاربر باید بفهمد چرا بیرون انداخته شده و چه کند |
| **مجوز بسته — بخش/تب داخل صفحه** | **کارت inline** (`renderDeniedNotice`) | جای محتوا نشان داده می‌شود، بدون خطا و بدون جابه‌جایی |
| شکست‌های پس‌زمینه (رفرش بی‌صدا، وضعیت خودکار پیامک، بررسی خودکار تغییرات) | ⚪ هیچ پیام — فقط `console` | صفر مزاحمت |
| لاگ‌های دیباگ (`✅ initialized`، `TOKEN_KEY`، `Cache`) | ⚪ فقط `console` | صفر مزاحمت |

- `notifyOnce` تضمین می‌کند پیام‌ها مزاحم نشوند:
  - **ضدتکرار**: همان پیام (`key`) در بازهٔ `cooldownMs` (پیش‌فرض ۳۰ ثانیه) دوباره نمایش داده نمی‌شود.
  - **سقف نرخ**: حداکثر `maxPerMinute` (پیش‌فرض ۳) پیام در دقیقه.
  - **یک پیام در لحظه**: اگر توست/مودال دیگری باز باشد، پیام در صف می‌ماند (تا ۱۰ ثانیه) و پیام‌ها روی هم انبار نمی‌شوند.
  - **خاموشی سراسری**: `localStorage.setItem("skb_user_toasts","off")` یا باز کردن صفحه با `?debug=1` → فقط کنسول.
  ```js
  notificationService.notifyOnce({
    key: "dict-status-change",
    type: "error",
    message: "تغییر وضعیت ذخیره نشد — دوباره تلاش کنید",
  });
  ```
- نقاط مشمول این سیاست (نگهبان خودکار در `npm run test:cache`):
  - `features/admin-panel/dictionary.manager.js` — تغییر وضعیت، بارگذاری جدول، گزینه‌های فیلد
  - `features/customer-info/customer-info.service.js` — رفرش یک بخش
  - `features/customer-info/section-header/section-header.service.js` — نبود شناسهٔ مشتری
  - `features/whats-new/whats-new.service.js` — شکست دریافت «تغییرات جدید»
  - `src/pages/login.html` — شکست کپچا + مودال «نشست منقضی شد»
  - `src/pages/customer-info.html` — بوت کند صفحه (یک‌بار در ۵ دقیقه)
  - `core/services/api.service.js` — ثبت فلگ انقضای نشست پیش از هدایت به `/login`

## «نظرات و پیشنهادات» (گفتگوی کاربر ↔ ادمین)

- کاربر: از **آیکون پاکت در هدر** یا صفحهٔ «تماس با ما» پیام می‌فرستد، پاسخ‌ها را همان‌جا با
  **بج تعداد نخوانده** می‌بیند و می‌تواند پاسخ بدهد.
- ادمین: در پنل مدیریت → بخش **«نظرات و پیشنهادات»** (جای «گفتگوی عمومی» قبلی که بک‌اند نداشت):
  لیست + فیلتر (وضعیت/نخوانده/جستجو) + بج تعداد نخوانده + مشاهدهٔ گفتگو + پاسخ + تغییر وضعیت.
- **حذف (فقط ادمین)**: روی هر ردیف فهرست یک آیکون سطل زباله هست (حذف کل گفتگو) و در فوتر
  گفتگو دکمهٔ «حذف گفتگو». داخل خود گفتگو هم روی هر پیام (به‌جز پیام اول) سطل زباله هست که
  فقط همان پیام را حذف می‌کند؛ اگر آخرین پیام حذف شود کل گفتگو هم پاک می‌شود.
  - `DELETE /api/suggestions/:id` → حذف کل گفتگو
  - `DELETE /api/suggestions/:id/messages/:messageId` → حذف یک پیام
- **ضد ارسال دوبار:** اگر همان کاربر در ۳۰ ثانیهٔ اخیر دقیقاً همان «موضوع + متن» را فرستاده

- **ترتیب مودال‌ها:** انتخاب گله (تاریخچه) → انتخاب شاخص‌ها → **انتخاب هفته‌ها**.
- **ساختار ترکیبی:** ناحیهٔ ① یک **انتخاب مشترک** برای همهٔ گله‌ها (همه · فقط ثبت‌شده · فقط مشکل‌دار · بازهٔ از/تا) و ناحیهٔ ② (جمع‌شده، اختیاری) **تنظیم جداگانهٔ هر گله**: پریست‌های خودش، لیست هفته‌ها با تاریخ و وضعیت (✅/🟡/❌)، «بازگشت به انتخاب مشترک» و شمارندهٔ «۳ از ۹ هفته».
- **کلید هر پنل:** در گزارش کامل هفتگی `p<placementId>` (هر سالن یک پنل) و در گزارش تاریخچه `f<flockId>` (هر گله یک پنل؛ هفته‌هایش = اجتماع سالن‌ها با قاعدهٔ «کل گله»).
- **قاعدهٔ مشترک روی هر گله جداگانه حل می‌شود** (مثلاً «فقط مشکل‌دار» برای هر گله هفته‌های خودش را می‌دهد) و انتخاب سفارشی هر گله اولویت دارد.
- **گلهٔ بدون هفتهٔ انتخابی** → نرم از گزارش حذف می‌شود + خط اطلاعی «N گله به‌خاطر انتخاب‌نشدن هیچ هفته‌ای نیامده است».
- **آلارم ثبت هفتگی** فقط روی هفته‌های داخل انتخاب همان گله محاسبه می‌شود + خط «N هفتهٔ مشکل‌دار دیگر خارج از انتخاب شماست».
- **جدول تجمعی «کل گله»** = اجتماع هفته‌های انتخاب‌شدهٔ سالن‌ها.
- **ذخیره:** فقط قاعدهٔ مشترک (پریست/بازه) در `localStorage["skb_weekly_report_weeks"]` می‌ماند؛ انتخاب‌های تک‌گله ذخیره نمی‌شوند.
- **پیش‌فرض = همهٔ هفته‌ها** ⇒ گزارش بدون دست‌زدن به تنظیمات، همان خروجی قبلی است؛ اگر SweetAlert2 نباشد مودال نمایش داده نمی‌شود و همهٔ هفته‌ها می‌آید.
- ⚠️ مجموع‌ها/FCR همچنان روی **همهٔ** هفته‌های ثبت‌شده محاسبه می‌شوند؛ این انتخاب فقط «کدام هفته‌ها نمایش داده شوند» را کنترل می‌کند (در راهنمای مودال هم نوشته شده).
- **منبع:** `weekly.report.weeks.js` → `buildWeekTimeline` · `resolvePresetWeeks` · `normalizeWeekSelection` · `effectiveWeeksFor` · `unionWeekSelection` · `mergeWeekTimelines` · `issuesOutsideSelection` · `summarizeWeekSelection` · `weekSelectionLabel` + مودال `weekly.service.js → pickReportWeeksPerFlock()`.

### 🔤 ترتیب ثابت سالن‌ها در گزارش‌ها (A → آخر)

- بک‌اند هیچ‌جا بر اساس نام سالن مرتب نمی‌کند (فقط `placement_date`) و include جوجه‌ریزی‌های گله هم `order` ندارد؛ پس ترتیب نمایش تصادفی/بر اساس id بود.

  - حروف لاتین **A → Z** (بدون حساسیت به بزرگی/کوچکی · کوتاه‌تر جلوتر: `A` قبل از `AA`)
  - سپس حروف فارسی/عربی بر اساس الفبا
  - سپس اعداد به‌صورت **عددی** (`سالن ۲` قبل از `سالن ۱۰`)

## نکات امنیتی مرتبط با این سرویس

- **`/uploads` عمومی است** (چون در `<img>/<video>/<iframe>` استفاده می‌شود و مرورگر
  روی این درخواست‌ها توکن نمی‌فرستد). برای همین بک‌اند این سخت‌گیری‌ها را اعمال می‌کند:
  پسوندهای اسکریپتی/اجرایی (`html`, `js`, `svg`, `exe`, …) هرگز سرو نمی‌شوند (۴۰۴)،
  `X-Content-Type-Options: nosniff` همیشه ست می‌شود و فایل‌های غیرتصویری با
  `Content-Disposition: attachment` (دانلود) فرستاده می‌شوند.
- محتوای آپلودشده **هرگز داخل مبدأ سایت اجرا نمی‌شود** (جلوگیری از سرقت توکن از localStorage).
- اگر روزی نوع فایل جدیدی لازم شد که در لیست مجاز نیست، در `Backend/server.js`
  مقدار `UPLOADS_INLINE_EXT` را به‌روز کن (نه اینکه کل محافظ را برداری).
- پنجره‌های چاپ/گزارش با `sanitizeHtmlDocument()` پاک‌سازی می‌شوند (فایل
  `src/core/utils/string.utils.js`) چون هم‌مبدأ با سایت‌اند و به `opener` دسترسی دارند.

## سطوح دسترسی (مدیریت نقش‌ها) — پنل مدیریت

بخش **«مدیریت نقش‌ها»** در پنل ادمین (منوی `data-menu="role-management"`) از این پس
کار می‌کند و سه زیرتب دارد:

| زیرتب | کار |
|---|---|
| **ماتریس نقش‌ها** | ۱۵۶ مجوز در ۱۵ گروه (آکاردئون) × ۵ نقش — سوییچ روشن/خاموش، جستجو، «فقط تغییرات»، بازگردانی نقش |
| **دسترسی کاربران** | انتخاب کاربر + سوییچ **سه‌حالته**: «ارثی از نقش» / «فعال» / «غیرفعال» + بازگردانی به سطح نقش |
| **گزارش تغییرات** | چه کسی، کِی، چه مجوزی را عوض کرد |

- تغییرات **فقط با دکمهٔ «ذخیره تغییرات»** اعمال می‌شوند؛ فوتر تعداد تغییرات ذخیره‌نشده را نشان می‌دهد.
- 🔒 مجوزهای حساس (مثل «حذف مشتری») فقط برای مدیر اصلی قابل فعال‌سازی‌اند و سوییچ‌شان قفل است.
- فقط **مدیر اصلی** می‌تواند تغییر دهد؛ بقیه حالت «فقط خواندن» می‌بینند.

### فایل‌ها

### منوهای سایدبار پنل = کلیدهای مجزا
نمایش/مخفی‌بودن هر منوی سایدبار با کلید مستقل خودش کنترل می‌شود (نه با کلیدهای محتوایی آن بخش):
`admin.menu.superAdmins` · `admin.menu.users` · `admin.menu.dictionary` · `admin.menu.roles` ·
`admin.menu.settings` · `admin.menu.suggestions` · `admin.menu.releases`

- مثال: خاموش‌کردن `dictionary.hall-types.view` فقط آن جدول را می‌بندد و **کل منوی دیکشنری‌ها را ناپدید نمی‌کند**.
- اگر منوی فعال مخفی شود، پنل خودش اولین منوی قاب‌مشاهده را فعال می‌کند؛ و اگر هیچ منویی مجاز نباشد پیام «هیچ بخشی برای نقش شما فعال نشده» نمایش داده می‌شود.
- اگر دریافت مجوزها خطا بدهد، منوها موقتاً بر اساس نقش نمایش داده می‌شوند (پنل خالی نمی‌شود).

### رفتار هنگام «نبود دسترسی» (۴۰۳)
| موقعیت | چه اتفاقی می‌افتد |
|---|---|
عملیات (ذخیره/حذف/تغییر وضعیت) که مجوزش بسته است | **توست**: «⛔ دسترسی «حذف سالن» برای نقش شما بسته است» (ضدتکرار ۳۰ ثانیه) — و بلافاصله مجوزها تازه می‌شوند تا منو/دکمهٔ مربوطه **همان لحظه** مخفی شود |
ورود به صفحه‌ای که کلیدش بسته است (`requiresPermission`) | **مودال تک‌دکمه‌ای**: «⛔ دسترسی به این صفحه بسته است — این بخش برای نقش «کارشناس» غیرفعال شده است: «ورود به پنل مدیریت». برای فعال‌سازی با مدیر اصلی تماس بگیرید.» + دکمهٔ «بازگشت به داشبورد». بار اول هر نشست مودال، بارهای بعد فقط توست |
بخش/تبی داخل صفحه (پروفایل مشتری، منوهای پنل) | **کارت inline** در همان بخش: «🔒 این بخش برای نقش شما غیرفعال شده است («مشاهدهٔ جدول مدیریت هفتگی»)»؛ محتوای بخش پنهان می‌شود و **هیچ درخواستی به سرور زده نمی‌شود**. با روشن‌شدن مجوز، کارت خودش برمی‌گردد |
مجوز در حین کار از کاربر گرفته شود | رویداد به همهٔ صفحه‌ها می‌رود (`permissions:applied`)؛ منو/دکمه‌ها مخفی و اگر مجوز خودِ صفحه بود، فوراً پیام + دکمهٔ بازگشت |

- کلیدهای صفحه: `admin.panel.access` · `customers.list.view` · `customer.basic.view` · `dashboard.view` · `bookmarks.view`
- کلیدهای بخش‌های پروفایل مشتری: `customer.basic.view` · `charts.view` · `halls.view` · `hatchery.view` · `weekly.view` · `visit.view`
- اگر مجوزها به‌دلیل خطای شبکه در دسترس نباشند، **هیچ‌چیز مسدود نمی‌شود** (fail-open) — پنل خالی نمی‌ماند.
- **ضدحلقهٔ ریدایرکت:** نقش «مشتری» از گیت صفحه مستثنا است و صفحهٔ مقصد (داشبورد) کسی را بیرون نمی‌اندازد؛
  در آن صفحه فقط پیام کوتاه نشان داده می‌شود.

### زمان اعمال تغییرات
| لایه | مقدار |
|---|---|
کش مرورگر (`permission.service.js`) | **۶۰ ثانیه** + بررسی نسخه (`/permissions/version`) + تازه‌سازی روی برگشت به تب/فوکوس |
کش سرور | ۳۰ ثانیه — ولی بعد از هر ذخیره در پنل همان لحظه پاک می‌شود |

⇒ تغییرات مجوز با **رفرش بعدی صفحه یا برگشت به تب** روی مرورگر کاربر دیده می‌شود؛ کنترل سرور از همان لحظهٔ ذخیره اعمال است.

### تست
```bat
npm run test:denied   :: پیام «عدم دسترسی» (۴۰۳ ⇒ توست + تازه‌سازی، کارت بخش، مودال تک‌دکمه‌ای، ضدحلقه)
npm run test:toast    :: کم‌مزاحمتی توست‌ها (ضدتکرار / سقف نرخ / خاموشی)
npm run test:cache    :: نگهبانهای UI (وجود بخش، سه‌حالته‌بودن، وجود سرویس و API)
```
